## 一套门店 POS 如何关联

| 系统 | 交换的信息 | 当前状态与接入前提 |
| --- | --- | --- |
| 菜单与订单 | 分类和菜品上下架、价格快照、桌台停用、堂食换桌、外带订单、退菜、多菜拆单、折扣 | 本项目已实现；一个数据库代表一家门店 |
| 后厨 KDS/厨打 | 新增菜品、退菜、制作进度 | KDS 已实现；专用厨打需确认打印机协议、分档口规则及断纸补打流程 |
| 收款与对账 | 应收金额、交易号、支付状态、退款、日终对账 | 现金已实现；外部终端收款和退款只能在交易完成后人工记录。微信/支付宝/银行卡需商户资质、服务商权限、回调验签、查单与退款对账 |
| 交班与财务 | 单店共用钱箱、备用金、营业中现金存取、收退款操作人、差额、班次历史、销售与退款 | 已实现一个共用钱箱的交班和基础报表；多实体钱箱、会计凭证、税务发票及银行流水未接入 |
| 扫码点餐/会员 | 顾客端菜单、桌台码、支付、会员身份 | 未实现；必须明确顾客入口、商户主体、订单归属和支付方案 |
| 库存/采购/配方 | 菜品 BOM、扣库、盘点、采购入库、成本 | 未实现；需先确定损耗、退菜回库及组合套餐规则 |
| 外卖平台 | 平台订单、接单、取消、配送、商品映射 | 未实现；需平台开放接口权限与门店授权，不能仅凭网页模拟对接 |
| 连锁总部/ERP | 门店主数据、价格、报表汇总、组织与权限 | 未实现；需多门店隔离、同步队列和冲突策略 |
| 设备 | 票据打印机、钱箱、客显、扫码枪、秤 | 浏览器可打印小票；其余需设备型号、驱动和现场验收 |

当前系统是一个可运行的**单门店基础收银闭环**，不是宣称已经连通支付机构、外卖平台或财务软件的全套生产集成。餐饮门店可以先用小范围、非商业试用数据验证流程，再依据目标门店的收款方式和设备选定适配器。对外集成应使用经服务商授权的接口，并记录请求、回调、重试、幂等与人工对账结果。

## 核心数据与权限

- 所有金额以分存储，服务端计算订单应收；订单行保存点单时的名称和价格。已发出的后厨票据保留历史，退菜产生独立取消票据。
- 数据库时间按 UTC 保存；页面、小票和日报按中国标准时间（Asia/Shanghai）展示与归日。销售归收款日，退款归实际退款日。
- `ADMIN` 管理账号和全部业务；`MANAGER` 管理菜单、折扣、退菜/作废、退款和报表；`CASHIER` 点单、出厨、收银和交班；`KITCHEN` 仅操作后厨票据。
- 服务端采用带 `HttpOnly`、`SameSite=Strict` 的会话 Cookie 和 CSRF 校验。正式跨设备部署应使用 HTTPS 并启用 `POS_SECURE_COOKIE=true`。登录尝试有本进程级限速；反向代理仍需配置访问限制。
- SQLite 使用 WAL 模式，数据库文件必须放在持久化卷。当前数据模型没有多门店、跨节点写入或离线同步能力。
- 多个在线页面定时读取最新订单；订单修改和结账提交时核对版本号，拒绝基于旧账单的操作。同步依赖网络连接及同一台服务，不能在离线状态继续写入。
- 一个数据库只允许一个未关闭的钱箱班次；员工可以共同收款，但开班人或店长才可清点交班。交班核对钱箱金额及未结订单快照，未结订单可确认后留给下一班。升级旧版数据库前须清点所有并行的个人班次，不能把不同实体钱箱的余额直接相加。

## 生产接入时要验收什么

1. 收款：订单号与渠道交易号唯一映射；回调验签、重复通知、超时查单、部分失败、退款状态及日终差异均有现场记录。
2. 后厨与设备：多次加菜和退菜只生成增量票据；断线、重连、重复打印及设备故障有人工处理流程。
3. 高峰期：真实设备和网络条件下验证订单并发、响应、备用服务及恢复时间。
4. 财务：核对现金、外部渠道实收、退款、手续费、抹零与营业报表口径。

涉及服务商能力，应以其当时的正式开发文档与商户授权为准，例如[客如云开放平台](https://open.keruyun.com/)与[支付宝服务商平台](https://open.alipay.com/paymentServicer/paymentServicer.htm)。平台文档的存在不代表本项目已经完成认证或接入。
